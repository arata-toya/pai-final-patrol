# V3 認識調整用の撮影と未確定時停止

## 確認した事実

ユーザーのCASE_Aでは、採用条件0.85を超えるcrackは166.741秒の1フレームだけ（0.8668、画像枠y=3、画像由来の距離1.912m）。その次から候補がなくなり、168.259秒・x=6.881mでnear_target_lostになった。停止条件の「異なる3フレーム」を満たしていない。画像やROS通信の途絶ではなく、領域抽出・分類が継続しなかった。描画と学習画像の差の詳細は実画像で確認する。

## 修正

- 通常モードでは3.2m以内のuncertainを異なる3フレームで観測したら、停止指令→実速度確認→REVIEW_REQUIREDにする。ひび割れ点検成功として保存せず、diagnostic_camera.png、diagnostic_crop.png等を保存する。near_target_lostも残す。
- captureモードを追加。クラス判定にかかわらず、共通枠の候補へ接近して停止・撮影する。ROI_BRAKING / CAPTURE_CONFIRMEDと記録し、AI_BRAKINGや通常のひび割れ点検とは区別する。
- 撮影走行は出力名を*_CASE_A_capture、summaryのmodeをcapture、capture_only=trueにする。レポートも「撮影データ（認識調整用）」と表示する。
- 撮影走行は通常の成功率集計から除外する。モデルの重み、採用閾値0.85、シーンの配置は変更しない。
- 撮影終了時にcapture_review_latest.tar.gzを自動で作成する。

## 導入（初回のみ）

ZIPをWindowsのデスクトップに保存し、PowerShellで実行する。V3のスクリプトだけバックアップ・更新する。V2は変更しない。

```powershell
Expand-Archive -LiteralPath "$env:USERPROFILE\Desktop\pai_award_v3_capture_fix.zip" -DestinationPath "$env:USERPROFILE\Desktop\pai_award_v3_capture_fix" -Force
docker exec -u ubuntu pai_ros2 cp -a /home/ubuntu/pai_award_v3/scripts /home/ubuntu/pai_award_v3/scripts_before_capture_fix
docker cp "$env:USERPROFILE\Desktop\pai_award_v3_capture_fix\pai_award_v3_fix\." pai_ros2:/home/ubuntu/pai_award_v3/
docker exec -u root pai_ros2 chown -R ubuntu:ubuntu /home/ubuntu/pai_award_v3
```

Ubuntuターミナル：

```bash
cd /home/ubuntu/pai_award_v3
bash scripts/start_all.sh CASE_A capture
```

撮影モードは準備後に自動開始し、候補3か所で停止・撮影して終点へ進む。qは途中終了。これは認識調整用の走行であり、ひび割れ検出成功とは数えない。DONE、FAULT、REVIEW_REQUIREDのいずれでも終了時の記録を残す。

終了後、Windows PowerShell：

```powershell
docker cp pai_ros2:/home/ubuntu/pai_award_v3/capture_review_latest.tar.gz "$env:USERPROFILE\Desktop\capture_review_latest.tar.gz"
```

このファイルをチャットに添付する。正常・汚れ・ひび割れの実際の描画とCNN入力を比較してから認識を修正する。正常モードの再評価はその後に行う。

## 検証

新規テスト5項目に加え、既存テストを修正した統合状態で制御・データ分離・終了処理を確認。ROSノードの出力パスとレポートを、ROSを起動しない代替オブジェクトで検証した。撮影モードのGazebo実走行は未確認。
